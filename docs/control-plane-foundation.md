# Control-plane identity foundation

This package introduces a metadata-only ASGI service at `app.control_plane.api:app`, intended to run separately from the ticket-processing application. Its separate browser console supports sign-in, workspace membership, invitations, runner metadata, and audit review. It validates OIDC bearer access tokens and stores verified identities, team workspaces, membership roles, invitations, and metadata audit events in a dedicated Postgres database configured by `SUPPORT_CONTROL_PLANE_DATABASE_URL`.

## Identity-provider contract

Configure `CONTROL_PLANE_OIDC_ISSUER`, `CONTROL_PLANE_OIDC_AUDIENCE`, `CONTROL_PLANE_OIDC_JWKS_URI`, and the public OIDC `CONTROL_PLANE_OIDC_CLIENT_ID`. Register the control-plane origin root (`https://your-control-plane.example/`) as an allowed redirect URI in the identity provider and allow that origin through CORS on its discovery, token, and JWKS endpoints for browser access. For local development, `npm run dev:control-plane` uses `http://127.0.0.1:5174/control-plane.html`; allow that exact localhost redirect only in a development identity-provider client. Keep the control-plane console on a separate origin from the support application. The browser uses Authorization Code with PKCE, verifies the signed ID token, and requests the configured API audience; no client secret belongs in the browser. The issuer and JWKS endpoint must be HTTPS. The API independently accepts only RS256-signed bearer JWTs with the exact configured issuer and audience, required `sub`, `iat`, and `exp` claims, and a verified email claim. User subjects are taken from the validated token. Workspace IDs and roles from request payloads never establish access. `GET /api/v1/auth/config` returns the browser-safe issuer, audience, and client ID; it does not return the JWKS URI.

Install the `control-plane` package extra to add PyJWT and its cryptographic backend. The API has no password table or local password authentication. Email sign-in and multi-factor policy are delegated to the configured OIDC identity provider. The console stores the access token in tab-scoped session storage and clears it on sign-out; there is no refresh-token or provider-logout integration yet. Production identity-provider settings, redirect allowlists, and token/session policy still require operator setup.

## Workspace API

- `GET /api/v1/me` returns the verified identity and its memberships.
- `GET /` serves the standalone workspace administration console when the frontend production assets are present. It manages control-plane metadata only and does not sign the user into or authorize the ticket-processing app.
- `GET/POST /api/v1/workspaces` lists accessible workspaces or creates one with the caller as Owner.
- `GET /api/v1/workspaces/{id}/members` requires workspace membership.
- `PATCH/DELETE /api/v1/workspaces/{id}/members/{subject}` applies Owner/Admin policy, preserves at least one Owner, restricts Admin-role grants and Admin removal to Owners, and records the authenticated actor.
- `POST/GET /api/v1/workspaces/{id}/invitations` creates bounded, one-time invitations or lists pending/history records for Owners/Admins. Admins can invite lower roles; only Owners can grant Admin or Owner. The raw random invitation token is returned once with `Cache-Control: no-store`; only its SHA-256 digest is stored.
- `POST /api/v1/invitations/{id}/redeem` requires a valid bearer identity whose verified email exactly matches the invitation.
- `GET /api/v1/workspaces/{id}/audit` exposes bounded metadata events to Owners/Admins.
- `POST/GET /api/v1/workspaces/{id}/runners` creates a one-time, hashed runner credential for Owners/Admins or lists runner metadata for workspace members. Credentials expire within 90 days; the raw token is returned once with `Cache-Control: no-store`.
- `POST /api/v1/runners/{id}/heartbeat` accepts the runner token in `X-Runner-Token`, updates only a timestamp, and rejects revoked or expired credentials. `DELETE /api/v1/workspaces/{id}/runners/{runner_id}` revokes a runner credential and writes an audit event.

The invitation token is not emailed yet; the authenticated workspace administrator must deliver the one-time link through an approved channel. Production onboarding still needs a verified email sender, rate limiting, abuse controls, recovery flows, and operational key-rotation policy.

## Runner session authorization bridge

The control plane can issue an initial short-lived workspace authorization token at `POST /api/v1/workspaces/{workspace_id}/runners/{runner_id}/session`. It first verifies the caller's external OIDC bearer token, then reads the caller's current role and runner state from Postgres. The workspace ID and runner audience come from the route, and the role comes only from the membership row; request-body roles are ignored. The response contains a three-minute maximum RS256 bearer token with issuer, subject, exact runner audience, workspace ID, runner ID, role, timestamps, and a random token ID. Its expiry is capped by the upstream identity token expiry. The response is marked `no-store`; tokens contain no ticket, draft, connector, or model content.

Configure `CONTROL_PLANE_SESSION_ISSUER`, `CONTROL_PLANE_SESSION_KEY_ID`, and `CONTROL_PLANE_SESSION_SIGNING_PRIVATE_KEY_PEM` from a secret manager. The private key must remain in the control plane. `/.well-known/runner-session-jwks.json` publishes only the active public key plus any overlap keys in `CONTROL_PLANE_SESSION_PREVIOUS_PUBLIC_KEYS_JSON`. For rotation, publish the new active key and the previous public key together, update runner verifiers to the new JWKS, then remove the old public key after all tokens signed by it have expired. Emergency removal invalidates outstanding tokens once verifiers refresh their 60-second JWKS cache. The endpoint currently has no application-level issuance quota, so public deployments must rate-limit it at ingress.

This bridge is not yet consumed by the support runner. The runner still rejects non-loopback hosts, and the token does not provide tenant isolation by itself. A revoked member or runner cannot receive a new token, but an already-issued token can remain usable for up to three minutes plus clock-skew allowance. Before using it for approval or publication, the runner must validate the token on every request, bind it to an immutable configured workspace and runner ID, enforce per-route roles, and recheck authorization immediately before external writes. Do not disable the runner's loopback guard or claim hosted workspace protection until that work and cross-workspace storage isolation are implemented and tested.

Do not expose the API publicly until it is behind HTTPS ingress and request limits are configured. The runner heartbeat credential is a bearer secret in `X-Runner-Token`; configure every proxy and request logger to redact that header. Heartbeats update Postgres on each request, so apply workspace and network-aware throttling before connecting real runners.

## Data separation and current limits

The control-plane database stores no ticket bodies, drafts, evidence, provider credentials, raw runner secrets, or workflow execution payloads. Keep this database separate from the customer runner's `SUPPORT_WORKFLOW_DATABASE_URL`; when both URLs are configured in one process, startup compares their configured Postgres host, port, and database name and fails closed when they point to the same target. This check cannot detect distinct DNS aliases for the same database service, so deployments must also use separate database identities and verify separation operationally. Runner enrollment, expiry, revocation, and timestamp-only heartbeats are metadata primitives only: they do not yet connect to the runner process, authorize runner APIs, scope execution data to a workspace, or deliver model/connector secrets. The new control-plane console is integrated with these metadata identities and workspace endpoints, but it does not sign the user into or authorize the ticket-processing app; that application remains loopback-only. Workspace isolation is proven only for these metadata endpoints. Automated credential renewal, secret delivery, browser/runner encryption, billing, chat connectors, and large-scale readiness remain future work.

Use `Dockerfile.control-plane` for the isolated service image. Supply an OIDC audience intended for this API and a dedicated Postgres URL through the deployment secret manager. Do not expose the current runner app to the network until every support-data route is migrated behind authenticated, workspace-scoped authorization.
